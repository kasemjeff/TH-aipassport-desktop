aipass gives away pro AI models behind a web chat. This bridge puts them in your terminal and points them at your local files — by driving a real, logged-in de.aipass.net tab instead of forging its requests.

The thesis

The session cookie never leaves the browser. The bridge and your terminal never see it. The one request that carries credentials runs as ordinary page JavaScript inside a first-party tab, where Chrome attaches the cookie itself — so there is no token to store, refresh, or leak.

Why it exists

The problem, and the shape of the answer

You have a browser login to a chat product with generous free models. You want those models in a script, a coding loop, an editor — anywhere that isn't a chat box.

The naive path is to copy the cookie out of the browser and replay the request from a script. That means storing a live credential, tracking its expiry, and re-authenticating when it rotates — plus every request now originates from an unrecognized client. The bridge takes the opposite path: it never handles the credential at all. The real request is issued from inside a tab that is already logged in, so it is genuinely first-party and Chrome supplies the cookie the same way it does for a click.

What sits in front is an OpenAI-compatible endpoint on 127.0.0.1:8787. Anything that speaks that protocol — a curl one-liner, the bundled chat CLI, the file-editing agent — points at it and works, while the traffic is quietly relayed through the browser.

rule 1 Fetch in the page, not the worker

A service-worker fetch has no top-level browsing context, so a SameSite=Lax session cookie is never attached. The request has to run in the page's MAIN world to count as first-party.

rule 2 Socket in the worker, not the page

An https:// page reaching http://127.0.0.1 hits mixed-content and Private Network Access checks. An extension request with host_permissions does not — so the long-lived connection lives in the background worker.

The data path

What one message actually does

A request enters as OpenAI JSON and leaves the browser as the exact form the aipass chat page submits. The steps in between are the whole job of the bridge.

the round trip
// 1 · client → bridge  (OpenAI shape)
POST /v1/chat/completions
{ "model": "claude-sonnet-5@default", "stream": true,
  "messages": [{ "role": "user", "content": "..." }] }

// 2 · bridge → extension  (a job, over SSE — no cookie)
event: job
data: { "jobId": "…", "conversationId": "40adc2adf1f043f7",
        "modelId": "…", "text": "the newest user message only" }

// 3 · page → aipass  (first-party, Chrome adds the cookie)
POST /actions/send-message/40adc2adf1f043f7
{ "modelId": "…", "imageAspectRatio": "1:1",
  "messages": [{ role, parts: [{ type: "text", text }] }] }

// 4 · aipass → page → bridge → client  (AI SDK stream, refolded to OpenAI)
data: {"type":"text-delta","delta":"..."}          → choices[].delta.content
data: {"type":"tool-input-available", ...}      → delta.reasoning_content
data: {"type":"finish","finishReason":"stop"}   → finish_reason

Server-side tools ride the same stream. When a model runs web_search, the tool-input / tool-output / source-url frames are surfaced as reasoning_content — visible as progress, invisible to a client that only reads content. Those tools are fixed on the server; they can't be extended, which is why local file editing is driven by prompt convention instead.

The contract

What the endpoint actually allows

These are not choices the bridge made — they are what the upstream accepts. Everything above is shaped to fit them.

reject

An assistant turn in the array → 403

A messages array containing an assistant message is refused by the edge before the model sees it. The web UI never sends one, because the server owns the history. So the bridge forwards only the newest user message.

keep

The server remembers the conversation

History lives server-side, keyed by conversation id. Multi-turn works exactly as it does in the web UI — you send one message, the context is already there.

reject

An invented conversation id → 404

Conversations are created by the server. A random id returns Conversation not found. The id is the first sixteen hex characters of the clientCreateRequestId you submit when creating one.

free

Web search comes with the model

Some models call web_search, image, video, audio or deep-research upstream. You receive the results folded in. The tool set is fixed and cannot be extended from the client.

Field notes

Tracing the 403

Most of the work here was not building the pipe — it was learning what the edge in front of aipass rejects. It is Google Cloud Armor (the tell: a bare <title>403</title> page with via: 1.1 google), and it scores requests rather than matching one rule. Each finding below is a real dead end and the fix that cleared it.

01

Auth is cookie-only, same-origin

design

The capture showed no bearer token — just the session cookie, checked by origin. That single fact decided the whole architecture: the request must run inside a first-party tab, not from a script holding a copied cookie.

fixRun the real fetch in the page's MAIN world; relay everything else.
02

A fresh random conversation id

404

Posting to a made-up id returned Conversation not found. The server owns conversation creation — the client can't just name one and start talking.

fixReuse the most recent conversation, then later create one via /chat.data.
03

An assistant turn in the transcript

403

Sending a full transcript to give the model context was rejected at the edge — at every size, plain or not. The one variable that mattered was an assistant-role message, which the web UI never sends.

fixForward only the last user message; let the server hold the history.
04

A conversation that stalled

409

An aborted stream leaves the server believing a generation is still running, and every later request to that conversation returns 409 Conflict. It does not clear on its own.

fixOn 404/409, rotate to the next most recent conversation and retry.
05

A README that said “localhost”

403 · SSRF

Once the agent read real files, Open http://localhost:3000 in a Next.js README tripped an SSRF rule. Not size, not tags — the loopback host itself. A URL to a public site passed fine.

fixSubstitute localhost/127.0.0.1 outbound, restore them on disk — bytes unchanged.
06

A package.json with node -e

403 · RCE

A script field shaped like code execution (node -e "…") matched an RCE rule. The agent reads package.json early in almost any task, so it was a landmine directly in the path.

fixSplit, then drop only the un-sendable line; keep the rest. And stop shipping such scripts.
07

The model refused the “tools”

refusal

Framed as a tool protocol, the model — whose real system prompt says its only tool is web search — correctly declined to “simulate fake commands.” The framing was the bug, not the model.

fixReframe as a person pasting files: “you write the lines, I run them.” No claim of tools.
08

Creating conversations on demand

solved

A capture of the chat page's “new chat” revealed POST /chat.data with intent=create-conversation. The returned id is just the first 16 hex of the request id you send — which is why ids always looked the way they did.

fixEach agent run now starts its own fresh conversation — no leaked history, no manual id.

Tests

How it verifies itself without a browser

The one thing tests can't reach is the live edge filter — it lives behind a real session. Everything else is covered, because the harness runs the actual bridge as a subprocess and a scriptable stand-in for the extension. Tests drive the real HTTP surface and run the real CLIs, not mocks of them.

the shape of a test
// script the model's replies; reject payloads that match a pattern,
// the way the real WAF would
const handler = scripted(['NEED file package.json', 'DONE'], {
  reject: (t) => /node\s+-e/.test(t),
});
const ext = await new FakeExtension(bridge.base, { onChat: handler }).connect();

const { out } = await agent(dir);
assert.match(out, /omitting 1 line/);          // redaction fired
assert.doesNotMatch(handler.sent.join(''), /node -e/); // never sent

Every failure in the field notes above is now a regression test: assistant-turn rejection, conversation rotation, a job surviving a mid-stream disconnect, loopback round-tripping unchanged to disk, split-and-resend, line redaction, the premature-DONE guard, refusing paths outside the project root.

Writing the harness found real bugs

Three of them, all test-side: stale extension connections leaking replies between tests; a thrown assertion skipping cleanup and cascading; an assertion that counted a rejected attempt as delivered. The kind of thing that makes a suite quietly lie later.

Adding a case is cheap

Script the replies with scripted([...]), pass reject to model a new filter rule, assert on the CLI output or the files on disk. No fixtures, no network, ~1.5s for the whole run.

Extend it

Where to take it next

  • →New edge rules will surface only in real runs. When a payload 403s, the failing fragment is printed. Add its trigger to the substitution or redaction list — each is a two-line change with a matching test.
  • →The agent's format is convention, not capability. NEED / EDIT / CREATE / RUN / DONE are parsed from prose. New verbs are a parser case plus a tool function plus a line in the preamble.
  • →Model choice is a runtime lever. Discovery is live from list-models; free-credit and thinking flags are exposed. Only gemini-3.1-flash-lite is free — heavier work draws on the credit pool.
  • →The reframing is fragile by nature. The server's own persona always pulls the other way. Scrupulous models hold the arrangement well; weaker ones drift, which the nudge loop catches. Worth revisiting as models change.
